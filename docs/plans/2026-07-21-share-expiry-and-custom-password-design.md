# Share-link expiry presets and custom passwords

Date: 2026-07-21
Repos: `hcfs`, `hippius-desktop-internal`, `hippius-console`
Status: design agreed, not yet implemented

## Goal

Two user-facing changes to the file-sharing feature:

1. **Expiry presets.** The sender picks how long a link lives: 24 hours, 7 days,
   30 days, or until they revoke it. Today every link is fixed at 24 hours.
2. **Custom passwords.** The sender can type their own password for a
   password-protected link instead of accepting the generated one. Today the
   password is always a random 20-character string, and only the macOS Finder
   path offers password protection at all.

Both features apply to every share surface: the macOS Finder right-click, the
desktop in-app drive share, and the console's browser share.

## What exists today

| Layer | Current behaviour |
| --- | --- |
| `hcfs-server` | `file_shares.expires_at TIMESTAMPTZ NOT NULL`, computed from `SHARE_TTL_HOURS = 24`. `insert_uploading` documents it as server-authoritative: "clients cannot extend their own shares." A reaper sweeps expired and revoked rows every 5 minutes, deletes storage blobs, and releases billed bytes dedup-aware. |
| `hcfs-client` | `create_share` mints a public link. `wrap_share_key(password, key)` is a separate free function: Argon2id (19 MiB, t=2, p=1) derives a wrapping key, XChaCha20-Poly1305 seals the share key, and the blob rides the URL as `#p=`. The server never sees any of it. |
| `hcfs-client-wasm` | Exports `unwrap_share_key` only — the console can *open* a private link but cannot *create* one. |
| Desktop | Finder path offers public vs. password-protected, with a password generated by `generate_share_password` (macOS-gated). The in-app drive share is public-only with no chooser. |
| Console | Its own `ShareFileModal` mints public links only. The recipient page already handles both `#k=` and `#p=`. |

Expiry is therefore a genuine server change; the password is a pure client
change.

## Defect this work must fix

`hcfs_list_shares` (`src-tauri/src/shares/commands.rs:728`) rebuilds every row's
URL with `build_share_url(...)` — a public `#k=` link — from the raw key in
`share_keystore`. It does this for password-protected shares too.

The cause is ordering. `make_private` mints a *public* share first, letting
`create_share` persist the raw key, and only then wraps that key and rewrites
the URL string. Nothing records that the share went private, and the raw key
stays on disk. The Shares page consequently offers a Copy button that hands out
a password-free link to a file the user chose to protect. The same ordering is
why `revoke_public_share` exists at all: it is a compensating action for the
public share that should never have been minted.

Shipping a custom-password feature on top of that page is not defensible, so the
fix is in scope.

## Decisions

| Question | Decision |
| --- | --- |
| Storage posture for never-expiring shares | Allow "never" for every share, including Finder "upload & share" of an outside file. The bytes stay billed to the owner in `user_summaries` until revocation, which is already the correct accounting. |
| Custom vs. generated password | Generate by default, allow overwrite. Selecting "Password protected" pre-fills a strong random password in an editable field. |
| Console scope | Full parity: expiry *and* password creation, which requires new wasm exports. |
| Changing expiry after creation | Yes — `PATCH /v1/shares/{token}`. |
| Changing the password after creation | No. A share's password is fixed when the link is minted. To hand out a different password, revoke the link and share the file again. |

## Design

### 1. hcfs-server

**Migration** `20260721000000_share_expiry_presets`:

```sql
ALTER TABLE file_shares ALTER COLUMN expires_at DROP NOT NULL;
```

`NULL` means never. Using NULL rather than a far-future sentinel keeps "never"
unrepresentable as a timestamp, so no query can mistake it for a long expiry and
no clock skew can turn it into one.

**New type** in `shares/types.rs`:

```rust
#[derive(Clone, Copy, Debug, Default, Deserialize, Serialize)]
#[serde(rename_all = "snake_case")]
pub enum ShareTtl {
    #[default]
    #[serde(rename = "24h")] Hours24,
    #[serde(rename = "7d")]  Days7,
    #[serde(rename = "30d")] Days30,
    Never,
}

impl ShareTtl {
    pub fn expires_at(self, now: DateTime<Utc>) -> Option<DateTime<Utc>> { .. }
}
```

`SHARE_TTL_HOURS` is deleted, not retained as a fallback. `ShareTtl::default()`
is `Hours24`, which is what a client omitting the field receives, so old clients
keep today's behaviour without a compatibility branch. Serde rejects any other
value, producing a 400 at the boundary.

The doc comment on `insert_uploading` changes from *server-authoritative* to
*server-validated*: the client selects from a closed set and the server still
computes the timestamp. Clients cannot name an arbitrary instant.

**Wire changes:**

- `CreateShareMetadata` and `InitShareRequest` gain `ttl: Option<ShareTtl>`.
- `expires_at` becomes `Option<String>` on `CreateShareResponse`,
  `ShareListItem`, and `ShareMetaResponse`. `null` means never, so recipients
  and the owner list learn about it without a second field.
- `NewShare` gains `ttl`; `insert_uploading` binds `Option<DateTime<Utc>>`.

**Liveness predicates** flip from `expires_at > NOW()` to
`(expires_at IS NULL OR expires_at > NOW())` in `get_meta_active`, `list_owner`,
and `authorize_chunked_caller`. The route guard at `routes.rs:614` becomes
`row.expires_at.is_some_and(|e| e < Utc::now())`.

**Reaper** `reap_batch` takes the mirror-image change: the complete-and-expired
arm becomes `expires_at IS NOT NULL AND expires_at < NOW()`. The
revoked arm and the stale-`uploading` arm are untouched — the latter already
keys off `created_at`, not `expires_at`, so orphaned uploads are still swept
regardless of TTL.

**New route** `PATCH /v1/shares/{token}`:

- Body `{ "ttl": "7d" }`; response `{ "expires_at": "..." | null }`.
- Owner-authenticated through the same bearer path as `revoke_share`.
- Eligible rows only: `upload_state = 'complete'`, `revoked_at IS NULL`, and not
  already expired. Everything else returns 404, matching revoke's rule that the
  endpoint must not leak whether a token exists. An already-expired row is
  excluded deliberately: its blob may already be reaped, so extending it would
  produce a link that resolves to nothing.

**Tests:** `shares_db.rs` (NULL round-trip, reaper skips never-expiring rows,
`list_owner` includes them), `shares_routes.rs` (each preset maps to the right
timestamp, unknown preset is a 400, PATCH authorization and the three 404
cases), and an end-to-end never-expiry path in
`hcfs-e2e-tests/tests/shares.rs`.

### 2. hcfs-client and hcfs-client-wasm

**Password moves into minting.** `create_share` accepts the password up front
and returns a `#p=` URL directly. `make_private` and `revoke_public_share` are
deleted — with no mint-then-wrap window, there is nothing to compensate for.

**Argument grouping.** `create_share` already carries an
`#[expect(clippy::too_many_arguments)]` waiver. Rather than widen it for `ttl`
and `password`, split on a real seam: the parameters the *user chose* move into
a borrowed options struct, while transport plumbing stays flat.

```rust
pub struct ShareOptions<'a> {
    pub filename: &'a str,
    pub mime_type: &'a str,
    pub ttl: ShareTtl,
    pub password: Option<&'a str>,
}
```

`reader`, `plaintext_size`, `keystore`, `console_base_url`, and `progress`
remain positional. The waiver is removed.

**Keystore stores a variant, not a key.** This is what makes the Section
"Defect" leak structurally impossible rather than conditionally avoided:

```rust
pub enum ShareSecret {
    /// Raw share key — yields a `#k=` URL.
    Public([u8; 32]),
    /// Password-wrapped blob — yields a `#p=` URL.
    Private(Vec<u8>),
}
```

A private share's raw key is never persisted, so no code path — present or
future — has the material to build a public URL for it. Re-copying from the
Shares page reproduces the original `#p=` URL byte-for-byte, because the wrapped
blob is exactly what was in the link; the password is neither needed nor stored.
`build_share_url` dispatches on the variant.

The owner loses the ability to decrypt their own private share without the
password. That is acceptable: they hold the source file, and `revoke_share`
needs only the token.

**Shared password policy.** `generate_share_password` moves out of the desktop
crate (where it is macOS-gated) into hcfs-client, joined by
`validate_share_password` enforcing a minimum of 8 characters. One
implementation, so desktop and console cannot drift.

**New wasm exports:** `wrap_share_key`, `build_share_url_private`,
`generate_share_password`, `validate_share_password`.
`cross_crate_equivalence.rs` already pins native-wrap → wasm-unwrap; add the
wasm-wrap → native-unwrap direction so the framing stays symmetric.

### 3. hippius-desktop

**Boundary type.** Following the existing `ShareVisibility::parse` pattern in
`finder_bridge/commands.rs`, the untrusted IPC strings collapse at the edge into
a type that cannot hold a contradictory combination:

```rust
enum ShareChoice { Public, Private { password: String } }
```

"Private with no password" and "public with a password" are unrepresentable
downstream. `validate_share_password` runs here, in Rust — the frontend never
decides whether a password is acceptable.

**IPC changes:**

- `hcfs_create_share(folder_label, relative_path, ttl, visibility, password, on_progress)`.
- `confirm_finder_share(request_id, visibility, ttl, password, on_progress)` —
  same parse, shared with the above.
- `ShareLink.expiresAt` becomes `Option<String>`.
- `ShareSummary` gains `isPrivate: bool` for the lock badge and the correct copy
  affordance; `expiresAt` becomes `Option<String>`; `share_url` is derived from
  the `ShareSecret` variant.
- New `hcfs_update_share_expiry(share_token, ttl)` → `PATCH /v1/shares/{token}`.

**`hcfs_reshare` is deleted.** Its own doc comment states the premise:
"effectively a TTL extension built out of the primitives we already have, since
hcfs-server doesn't expose an 'extend share' endpoint." That endpoint now
exists. Its only other plausible use — reminting after the keystore lost the key
— is unreachable, because the `share_origin` row reshare needs lives in the same
SQLite database as the key and disappears with it. The `share_origin` table
stays, since it powers the per-file `SharedLinkBadge`; only the command and its
button go.

This does not cost a password-rotation path, because there is deliberately no
such path — see "A share's password is immutable" below.

**UI.** `ShareFileModal`'s `choose` step stops being Finder-only and becomes the
shared first screen for both entry points — `DriveContent` and
`FileViewerLayout` no longer jump straight to `running`. It carries a visibility
toggle, an expiry select (24 hours / 7 days / 30 days / Until I revoke), and, on
the private branch, an editable password field pre-filled with a generated
value. The Shares page gains a lock badge, renders "Never expires" in place of a
countdown, and offers a per-row expiry dropdown.

**Tests:** boundary-parse unit tests for `ShareChoice`; `ShareFileModal.test.tsx`
for the chooser and the password default; `shareRowDisplay.test.ts` for
null-expiry formatting. The `fn_body` source-pin test currently anchored on
`hcfs_reshare` needs retargeting.

### 4. hippius-console

**Blocker:** `src/app/api/hcfs/[...path]/route.ts` exports `GET`, `DELETE`,
`POST`, and `PUT`. Next.js App Router answers only exported methods, so
`PATCH /api/hcfs/v1/shares/{token}` returns 405 before reaching hcfs-server. A
`PATCH` export is required. It carries a body, so it follows the `POST`/`PUT`
shape rather than the bodyless `GET | DELETE` forward helper at line 82. Desktop
talks to hcfs-server directly and does not hit this.

**Creation** (`src/lib/files/share/share.ts`): `CreateShareInput` gains `ttl` and
optional `password`; both the single-shot metadata and the chunked init body
carry `ttl`. With a password, `createShare` calls the new wasm `wrap_share_key`
and builds a `#p=` URL. `ShareLink.expiresAt` becomes `string | null`.

**Keystore** (`src/lib/files/share/keystore.ts`): mirrors the `ShareSecret`
split. The private branch stores the wrapped blob — plain bytes, no wasm handle,
so no `.free()` bookkeeping — and frees the raw `SecretBytes` immediately. Same
structural guarantee as desktop.

**UI:** `ShareFileModal` gains the same visibility, expiry, and password
controls as desktop. `SharesPageClient` gains the lock badge, "Never expires",
and the per-row expiry dropdown.

**Recipient page** (`src/app/share/[token]/page.tsx`): already handles `#p=`, so
the password work is zero. It needs only to render "This link doesn't expire"
when `expires_at` is null.

### 5. A share's password is immutable

Expiry is mutable; the password is not. Once a link is minted, its password is
fixed for the life of that link. To hand out a different password, the sender
revokes the link and shares the file again, producing a new token and a new URL.

This is a product rule, not a limitation we intend to lift, and the architecture
already matches it:

- The server holds no key material at all, so it has nothing to re-wrap.
- A private share's raw key is deliberately never persisted (`ShareSecret` stores
  only the wrapped blob), so the client cannot re-wrap it under a new password
  either — not without prompting for the *old* password to unwrap first, which
  would be a worse experience than reissuing the link.
- Reissuing is the honest operation anyway: anyone who already has the old link
  and old password keeps working access until the old token is revoked, so
  "changing the password" without revocation would be security theatre.

Implications for the UI in both desktop and console:

- The Shares page shows no "change password" affordance on private rows. The
  per-row action list is Copy, Change expiry, and Revoke.
- The share modal's password field is editable only on the create screen. Once
  the modal reaches its `done` state the password is display-and-copy only.
- Copy for a private row reproduces the original `#p=` URL from the stored
  wrapped blob. It does not reveal the password, which the sender is responsible
  for having conveyed out of band at creation time.

## Rollout order

The repos must land in dependency order, since desktop pins hcfs-client by git
rev and console pins the wasm build.

1. **hcfs** — server migration, `ShareTtl`, PATCH route, client `ShareOptions` /
   `ShareSecret` / password helpers, wasm exports. One PR; the server and client
   changes are coupled by the wire contract.
2. **hippius-desktop** — repin `hcfs-client` to the merged rev, then the IPC,
   keystore, and UI changes. This is where the `#k=` leak is closed.
3. **hippius-console** — rebuild wasm, add the `PATCH` proxy export, then the
   creation, keystore, and UI changes.

Deploying the server ahead of the clients is safe: `ttl` is optional and
defaults to 24 hours, so existing desktop and console builds keep working
unchanged.

## Out of scope

- Per-share download limits or view counts.
- Notifying the owner when a link is accessed.
- Bounding the "upload & share" zip size, which is an existing, separately
  tracked limitation in `share_directory_as_zip`.
