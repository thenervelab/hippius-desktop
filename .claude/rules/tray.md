# System tray and popover panel

Backend: `tray/geometry.rs` (pure, OS-agnostic anchoring math — which screen edge the panel drops from, on-screen clamping, fully unit-tested) and `tray/panel.rs` (the borderless `tray-panel` window lifecycle + `toggle_tray_panel` / `hide_tray_panel` IPC).

## Tray popover panel

The native tray menu is replaced by a borderless, transparent, always-on-top webview window (label `tray-panel`, route `/tray-panel`) anchored to the tray icon, opened on **left-click**.

**Right-click shows a small native context menu** (Open Files / Open Virtual Machines / Quit Hippius) built by `buildTrayContextMenu` in `useTraySync.ts` and attached to the icon with `showMenuOnLeftClick: false` so it never hijacks the left click; "Open Hippius" is omitted because the popover already has that button. The context menu's Open Files/VM items are tracked in the module-level `openFilesItem`/`openVmItem` so the existing login-status watcher enables/disables them.

Flow: a left click reaches Rust's own tray listener (`Builder::on_tray_icon_event` in `main.rs` → `tray::panel::on_tray_icon_event`, which checks Left + Up + `TRAY_ID`), never a webview callback. `TrayIcon.new` in `useTraySync.ts` gets NO `action`: that callback lives in the main window's page, and after a reload of the page (dev reload, the error screen's navigation) the icon kept calling a dead callback and the popover never opened again; the reloaded page found the icon already there and did not remake it (see the reload paragraph below). `on_left_click` routes via `capture::commands::on_tray_click` (see screen-capture.md) and `toggle_panel` places it with the icon's `rect`; Rust resolves the monitor under the icon, computes placement via the pure `tray::geometry::compute_panel_position` (drop below when the icon is in the top half of its work area (macOS menu bar / top taskbar), else rise above; centre on the icon and clamp on-screen; all physical px), then positions+shows the reused window (or hides it if already visible: a toggle).

**macOS: the context menu is kept off the status item** (`tray/status_menu.rs`). On newer macOS (seen on macOS 27) a status item that owns a menu (`NSStatusItem.menu`, which `TrayIcon.new({ menu })` and `setMenu` set) opens that menu on EVERY click, before `tray-icon`'s click view (`TaoTrayTarget`) gets the mouse down: no `Click` event reached Rust, a left click showed the small context menu, and the popover never opened. `showMenuOnLeftClick: false` cannot help (it only steers the click view, which never gets the event); hover events still arrive, from the view's tracking area. So `useTraySync.ts` calls `tray_menu_attached` (`reportMenuAttached`) after every `TrayIcon.new` and `setMenu`, and Rust takes the menu off the status item and keeps it (retained); a hover (`Enter`/`Move`) over the icon detaches it too, as a safety net. A right button down attaches the kept menu, `performClick`s the button (as `tray-icon` does) and takes it off again. `status_menu::on_tray_event` is called from the app's ONE tray listener (`tray::panel::on_tray_icon_event`), before the left-click route; never register a second `on_tray_icon_event` for it, or every click is handled twice. Windows and Linux are untouched (`imp` is a no-op there). Every click, route and show/hide decision is logged at `info` (`Hippius::tray::*`), so a click that did nothing still leaves evidence in `~/.hippius/logs`. Pinned by `tests/tray_popover_wiring.rs`, `tests/tray_status_menu_wiring.rs` (one listener, one `tray_menu_attached` registration, a report after every attach), the `status_menu` unit tests and `useTraySync.test.tsx`.

**A page reload rebuilds the icon.** The context menu's item callbacks belong to the page that made them and die with a reload, and the reloaded page cannot know what the icon shows, so `useTrayInit` closes an icon it finds already there and creates a fresh one (with its report). The new icon has none of a running recording's marks (the time, the Windows/Linux dot, the Linux recording menu), so `tray_menu_attached` also calls `capture::commands::restore_recording_in_tray`, which writes them back while a recording runs or is paused (`tray_status::text_to_restore`; a paused time never ticks to rewrite itself). The same report after the Linux `reattachTrayMenu` puts the recording menu back if a recording started meanwhile.

### Linux: no popover, menu opens the main window

Tauri's `tray-icon` crate fires no left-click `action` event on Linux, the app cannot self-position a window under Wayland, and there is no native vibrancy — so the rich popover is a **macOS/Windows-only** feature and Linux never shows it. On Linux the icon is built with `showMenuOnLeftClick: true` and the context menu leads with an **"Open Hippius"** item whose action simply **reveals the main window** (`openHippiusFromTray` → `openAppWindow`).

While a screen recording runs on Linux, Rust replaces this menu with the recording's own (Stop, Pause or Resume, Show recording controls; `capture/tray_recording_menu.rs`) and marks the icon; on `capture_tray_icon_released` the page puts its own menu back (`reattachTrayMenu`), since only it can rebuild items whose actions live in the page.

The Linux branch is gated on `isLinuxPlatform`, detected **synchronously** from `navigator.userAgent` (`detectLinuxPlatform`) — NOT the async `get_platform_info` IPC, which when late/failed left the flag `false` and silently dropped both the menu item and `showMenuOnLeftClick`, breaking the Linux tray entirely. `handleTrayClick` stays attached but is a harmless no-op on Linux.

**Windows** keeps the icon-anchored popover (its left-click `action` fires); off macOS the FE (`page.tsx` `cardSurface`) paints an **opaque** card + hairline border instead of the macOS translucent/vibrancy card (a 0.7-alpha card over the transparent window otherwise shows the desktop through). The native window shadow is macOS-only (`.shadow(cfg!(target_os = "macos"))`); the vibrancy `effects` call is left unconditional (Tauri no-ops it off macOS). `toggle_tray_panel` still takes `Option<TrayIconRect>` with a `fallback_anchor` (top-right) for the `None` case, but Linux no longer drives it.

### Key details

- **Linux/Windows window close actually quits.** `prevent_close()` is macOS-only (hide-to-tray). On Linux/Windows, `CloseRequested` must not cancel the close: doing so and then `exit(0)` from inside the GTK/WebKit handler orphans `/usr/bin/Hippius` in state S (H-003). Both the window X and tray Quit go through `tray::panel::quit_desktop`, which destroys `PANEL_LABEL` *then* `exit(0)` so the prewarmed hidden webview cannot keep the event loop alive. Pinned by `tests/window_close_wiring.rs`.
- **Click-outside dismissal**: the global `on_window_event` handler in `main.rs` calls `tray::panel::on_panel_blur` on `WindowEvent::Focused(false)` for the panel, which hides it and records `AppState.tray_panel_hidden_at`. `toggle_tray_panel` consults that timestamp against `REOPEN_COOLDOWN_MS` so clicking the icon of an open panel (blur → hide → toggle) reads as a dismiss, not an immediate re-open. A blur within `SHOW_SETTLE_MS` of a show (`AppState.tray_panel_shown_at`, `blur_dismisses`) gives the panel focus back instead: activating the app can hand the keyboard to the window that last had it (a capture card or pill the user clicked), which hid the popover the moment it appeared.
- **Window level**: on macOS every show puts the panel at `PANEL_WINDOW_LEVEL` (`NSPopUpMenuWindowLevel`, 101) with `FullScreenAuxiliary` (`raise_above_capture_surfaces`). `always_on_top` alone is `NSFloatingWindowLevel`, the capture preview card's level, and the card (316x330, bottom-right, ordered front whenever it shows, a failed one stays) covered the popover's lower half on laptop displays. Still below the capture overlays (1000) and camera bubble (1001). Pinned by `tests/tray_popover_wiring.rs` and the `tray::panel` unit tests.
- **Sync vs static-export URL**: `build_panel` picks `tray-panel` under `cfg!(dev)` (Next dev server serves the route) and `tray-panel.html` otherwise (the no-`trailingSlash` static export emits that file at the dist root; Tauri's directory fallback would otherwise look for the non-existent `tray-panel/index.html`).
- **Transparency**: requires `app.macOSPrivateApi: true` in `tauri.conf.json` **and** the `macos-private-api` Cargo feature on `tauri`. The `tray-panel` window label is added to the `default` capability's `windows` list. The native window shadow is disabled because on a transparent window it is computed from the rectangular bounds (a dark rectangle around the rounded card); the card's CSS `box-shadow` provides the shadow instead.
- **The card must NOT fill the window edge-to-edge.** It is wrapped in a transparent, full-window padded shell (`.tray-panel-shell` = `h-screen w-screen` + asymmetric padding: small top so the card hugs the icon, larger sides/bottom where the downward shadow casts) and fills the padded area via flex (`flex-1 min-h-0`). When the card was `w-screen h-screen` it matched the rectangular window exactly, so its `box-shadow` rendered entirely outside the window and was clipped everywhere except the four rounded-corner notches; since every shadow layer offsets downward, the bottom corners filled with dark triangles. The shell's padding turns those notches into transparent desktop and gives the shadow room to render as real elevation; the shadow's reach (offset + blur) is kept within the padding on each side so it is never hard-clipped at the window edge.
- **Theming & shared UI**: the popover follows the user's System/Light/Dark preference via the `.dark` class applied by `AppThemeProvider`, which the tray-panel branch of `AppShell` also mounts, reproduces the app background-image tone as a CSS gradient (light + dark), and reuses the app's shared `Button`, `HippiusLogo`, `BoxSimple` and `boring-avatars` identicon plus the sidebar's search-pill styling. The live chain block number under the account address is mirrored from the `block_number_updated` broadcast (`app.emit` reaches every window), avoiding a panel-local block subscription.
- **Header balance and footer identity come from `get_tray_menu_data`.** The header quotes `balance` (the billing API's exact decimal string) through `formatBalanceUsd` as "Balance $x.yy", never the `credits` f64 and never `toLocaleString` (which printed "0,36" on a French locale). The footer leads an OAuth account with `accountLabel` (resolved in Rust by `tray_menu::sign_in_label`, mirroring the sidebar's `resolveAccountIdentity`: email, `@handle` for GitHub, else username; placeholder `@hippius.local` emails dropped) over its SS58 in small type, and keeps the short address + live block only for an access-key account (`accountLabel` null). The identity is read via `auth_session_repo::get_identity`, which never touches the OS keychain because the popover polls every few seconds. Pinned by `app/tray-panel/__tests__/trayPanelAccount.test.tsx` and the `tray_menu` unit tests.
- **Window isolation**: `AppShell` renders the popover with no app providers, so it never creates a second tray icon or duplicates background work.
- **Notification bell**: the popover bell shows the live unread badge (via `get_unread_count` keyed by the account address — the same DB value the top-bar bell shows) and, on click, focuses the main window and emits `hippius:tray-open-notifications`, which the top-bar `NotificationMenu` listens for. The popover deliberately does NOT render the notifications menu itself — that component runs notification-_generator_ hooks (`useCreditsNotification`, `useFilesNotification`, `useNotifications`), so mounting it in a second window would duplicate notifications and API polls.
- **Chat unread button**: while team chat has unread DMs/mentions, a chat button carrying that count sits before the bell (absent at zero, so a user without chat sees the header unchanged). The count is the number Rust puts on the dock badge and in the `(N) Hippius` window title: `useTrayPanelData` seeds `chatUnread` from `chat_get_unread_count` (the popover is prewarmed, so a count set before it listened would otherwise be missed) and follows the `chat_unread_changed` broadcast. Click → `revealMain()` + `hippius:tray-open-chat`, routed to `/chat` by `TrayNavigationListener` in the main window — the popover never navigates itself.
- **During a screen recording Rust owns the icon's title and click** (see `.claude/rules/screen-capture.md`, "Menu bar"): the title is written from `capture::commands::emit_phase` (only when it changes), and every left click asks `capture::commands::on_tray_click` first. **A signed-in click opens the popover in every capture phase** (`TrayClickRoute::TogglePanel { recording }`); a recording also brings its pill back and shows the popover with content protection on, so it is not filmed. Routing a recording's click to the pill alone left the icon doing nothing visible (the pill was already up); only a signed-out click mid-recording is pill-only. On Windows Rust also draws the recording's dot on the icon and, when the recording ends, emits `capture_tray_icon_released`, the one capture event `useTraySync.ts` listens to (it re-applies the icon it last asked for). `useTraySync.ts` neither writes the title, handles the click nor reads the capture phase; pinned by `tests/capture_wiring.rs` and `useTraySync.test.tsx`.
- **Signed-out behavior**: the popover only opens when signed in. `useTrayInit` reports the auth context's `isAuthenticated` to Rust (`tray_set_signed_in` → `AppState.tray_signed_in`) whenever it changes and on every page load; a signed-out click brings the main window forward instead (`TrayClickRoute::OpenMainWindow`). It starts `false`, so a click before the page reports opens the app. **Do not** gate this on Rust's `AuthInfo.substrate_address`: that stays populated for a session restored from disk even while the UI is logged out, so it would wrongly open the popover. The `toggle_tray_panel` IPC remains and routes the same way.

### Known limitations

1. On **Linux** the rich popover is not shown at all; a true Linux popover would need a layer-shell surface Tauri's tray doesn't expose.
2. On macOS a plain always-on-top window activates the app on click (an `NSPanel` non-activating window is the eventual fix).

The old unattached full in-memory `Menu`/submenu machinery has been removed; `useTraySync.ts` attaches only the small `buildTrayContextMenu` right-click menu and drives the icon from the pure `tray/trayIconState.ts`.

## Tray panel UI (`app/tray-panel/page.tsx`)

A top-level route so it skips the `(pages)` sidebar layout. Self-contained: talks to the backend only via `invoke`, fetches its feed through `app/lib/tray/useTrayPanelData.ts`, and reuses shared app components (`NoEntriesFound` empty state, `Button`, `HippiusLogo`, `boring-avatars`).

It addresses the main window by its `"main"` label and drives it via events rather than navigating itself: **Open Hippius** just reveals main; the **bell** emits `hippius:tray-open-notifications`; **Search Files** emits `hippius:tray-focus-search` (focuses the sidebar `SidebarSearch`); the empty-state **Upload a File** CTA emits `hippius:tray-open-files` (navigates main to `/files` via `TrayNavigationListener`). It deliberately does NOT `router.push` a protected route from the popover webview, and uses a **static** `import { emit }` (not a dynamic `import()`) — a dynamic import in the isolated panel webview can fail to load its chunk and surface as a runtime/"internal server" error.

Under the search pill, **`TrayCaptureRow`** (behind `SCREEN_CAPTURE_ENABLED` and Rust's `capture_support`, read through the pure `trayCaptureView`; skeleton while asking, absent where capture is off or unsupported) offers Screenshot and Record as split buttons: the body starts that kind on its last mode, the chevron opens the Drive page's mode menu plus "Change capture drive…" (classes and labels shared from `CaptureButtons`). A press hides the popover FIRST, then emits `hippius:tray-capture` (`TRAY_CAPTURE_EVENT`) for the main window's `CaptureHost` to run through `useStartCapture`, because the drive picker and permission explainer are main-window dialogs; the drive item emits `TRAY_CAPTURE_DRIVE_EVENT`. An open menu closes on window blur, or the next open shows it still open. The header holds no capture button (it is kept as staging has it). Buttons use the shared `Button`'s `subtle` variant (the search pill's fill, no corner dots, a focus ring).

Above the date-grouped upload list (under the "Your Uploads" heading) it renders a **sync-progress summary** (`SyncSummary`) — percent + status word ("In Progress" / "Complete" / "Failed" / "Preparing") + a synced-vs-remaining line — driven by the pure `app/lib/tray/traySyncSummary.ts::getTraySyncSummary` resolver (mirrors the sidebar `SyncStatusDialog`; returns `null` when idle). The live snapshot it reads is exposed from `useTrayPanelData` (seeded via `sp_get_snapshot`, updated by `sync_progress_snapshot` events).

## Tray sync state cleanup

The tray-icon watcher in `useTraySync.ts` keeps module-level latch state (`latchedComplete`, `latchedSnapshot`, `lastSyncSummarySignature`) so a completed sync's icon survives the backend resetting its snapshot to an empty cycle; the latch *transition* logic itself is the pure, unit-tested `app/lib/tray/trayIconState.ts::deriveTrayIconState` (the watcher just stores its result). These are explicitly cleared in the `useTrayInit` logout cleanup effect to prevent stale data from a previous account appearing after account switch.
