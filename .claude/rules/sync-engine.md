# Sync engine

## Module map

The ~32 submodules are organized into six private sub-domain group directories, each re-exported at `crate::sync::<module>` from `mod.rs` — the grouping is a file-tree layer that leaves every `crate::sync::<module>::<item>` path unchanged. Cross-submodule helpers are `pub(super)` and reached via `super::<mod>::<item>`.

| Group | Modules |
|---|---|
| `drive/` | `lifecycle.rs` (init, auto-init, teardown, progress handler setup), `lifecycle_guard.rs` (per-label epoch model + `apply_init_commit`), `drive_status.rs`, `control.rs` (start/stop/pause), `config.rs` (HCFS config loading), `paths.rs` (sync path DB ops), `selective.rs`, `device.rs`, `identity.rs` |
| `projection/` | `progress.rs` (in-memory session/file progress), `preparing.rs`, `status.rs` (sync status queries), `logic.rs` (pure I/O-free helpers: snapshot throttling), `intent.rs`, `upload_processing.rs`, `tauri_bridge.rs` (OnceLock-based event dispatch to Tauri), `events.rs` (event name constants + payload structs) |
| `fileops/` | `files/`, `folders.rs` (folder CRUD + remote origin classification), `remote.rs`, `recent_uploads.rs` |
| `migrate/` | `migration.rs` (S3→HCFS: check, start, poll, `complete_migration_transition`), `relative_path_backfill*`, `folder_entries_backfill.rs`, `folder_entries_materialize.rs`, `folder_entries_reconcile.rs`, `user_stopped_*` |
| `failure/` | `failure_*`, `error_notify.rs`, `credits_exhausted.rs` |
| `shared/` | `mnemonic.rs`, `region.rs`, `chunk_reclaim.rs` |

`files/` is itself split by sub-domain, and `mod.rs` re-exports every IPC handler so all `crate::sync::files::X` paths are unchanged:

- `asset_scope.rs` (asset-protocol scope), `add.rs` (add file/folder + batch + the upload byte/count walkers — `walk_regular_files_stats_std` skips the same names Drive listing hides (`.` prefix, failed-download artifacts, 0-byte encrypted-name stubs) so the File No banner cannot count a file the table omits; hidden files are still copied onto disk. **The `.`-prefix rule is `is_engine_hidden_name`, a `to_str()`-gated mirror of hcfs's `drive::exclude::should_skip_path`, shared with `compute_startup_pending_summary_std`** — the counters exist to predict engine work, so a name the engine uploads (a non-UTF-8 `.`-name, which upstream does NOT skip) must stay counted, and the rule is the leading dot on every platform because listing and the engine both key off it there. All three of `add_file` / `add_files` / `add_folder` invalidate the dir-stats cache after a copy via `invalidate_dir_stats_for_change`, against the RAW `sync_path` — listing keys the cache by the path the frontend passed, so the canonical form would miss on macOS), `delete.rs`, `rename.rs`, `recent.rs` (recent files + the shared per-drive `synced_paths_*` reads), `dir_stats.rs` (cached recursive dir size/count; nested deletes must invalidate ancestors), `listing.rs` (flat + grouped listing, owns `FileEntry`), `user_files.rs` (files page + recursive search + filter cascade, owns `UserFileEntry`; a `search_term` with `*`/`?` is a globset glob against the relative path, otherwise a substring of the display name or hash), `resolve.rs` (path resolve + single-file `export_file`), `export_zip.rs` (store-only `export_folder_zip`).
- `pathops.rs` is a **dependency-free leaf** holding the shared path helpers `ensure_within`/`derive_relative_name`/`copy_dir_recursive`, so the submodules form a DAG — it breaks the `add`↔`resolve` cycle.
- **Every copy into the sync root goes via a hidden `.hippius-incoming-*` sibling, then `rename`.** Both `add_folder` (new dest) and `add_file`/`add_files`. The live watcher would otherwise hash a growing tree, and `fs::copy` onto an existing path truncates before it refills, so a direct write lets a scan see a file shorter than the synced copy. hcfs carried a guard for that and **removed it in #367** — it could not distinguish a stalled copy from a finished smaller edit, so it delayed every legitimate shrink by a cycle — and its accepted residual names this staging as the replacement. The sibling is in the same directory, so the `rename` is atomic rather than a copy, and hcfs-client skips `.*` names in `collect_files` while it grows. **Gap:** `add_folder` onto an EXISTING dest still merges in place through hcfs's own `copy_dir_recursive`, so that path is unstaged; closing it is an hcfs change.

## Remote folder listing origin (H-077)

`get_sync_folders_with_stats` (`folders.rs`) puts any server folder whose hash is not in local `sync_paths` into `remote`. `remove_drive` deletes the local row but does **not** unregister the server folder (that is Delete from Server), so the folder reappears stamped with THIS device's `device_name`. Classify that row `RemoteFolderOrigin::LocallyRemoved` via `classify_remote_origin(raw_device_name, get_device_name_internal())` — empty names fail closed to `OtherDevice`. The FE keys the "Not synced on this computer" vs "Sync from Other Devices" split on the tagged `origin` field and must not re-compare names.

## Remote browse and account-wide search

**`remote.rs`** — remote folder operations: `list_remote_folder_files`, plus `download_remote_file` and `cache_remote_file`. Both download + decrypt a single **non-synced** file via the `hcfs_config.drive_password` → master-mnemonic → folder-key path, with no password prompt. `download_remote_file` writes to a caller-chosen path; `cache_remote_file` writes to a content-addressed preview cache and returns the path so the FE preview dialogs can `convertFileSrc` a cloud-only file. The `file_id` they take is hex of the server `path_hash`, threaded onto `UserFileEntry` by the search mapper.

**`recent_uploads.rs`** — owns `get_recent_uploads` AND `search_files`. Both hit the HCFS server's `/search_files` endpoint through a shared `fetch_search_files` core: a one-shot Arion call via `region::resolve_base_url` + `tokens::get_api_token` that maps hits onto `UserFileEntry`.

- `get_recent_uploads` sends `sort_by=created_at&sort_order=desc` for the empty-state "last uploads" slice.
- `search_files` builds the console's query params via the pure, unit-tested `build_search_query` (`q` + file_type/size/date filters + sort mapping) and backs the sidebar palette's cross-folder text search — the cloud equivalent of the local `search_user_files_recursive`, so uploads from other devices are found too.

**`sync_status` semantics**: a hit is `pending` ONLY when its drive label is configured on this device AND the file is not yet on disk — a genuine "queued for local download" state, probed via an injected `path_exists` predicate so the mapper stays pure/unit-testable. Files whose drive label isn't configured here (uploaded from another device, or under a removed-or-renamed label) and files already on disk are `synced`. The earlier rule — `pending` whenever the label wasn't configured locally — perpetually mislabeled stable server-only files as "Waiting in the sync queue".

## Member drives: the local label is NOT the wire identity

A drive in `sync_paths` may be a **member drive** — one that lives in another account's server namespace. Full rules in `shares-and-shared-drives.md`; the part that binds every drive-scoped site in `sync/`:

- **Never derive the wire hash from the local label.** `folder_hash(local_label)` is correct only for own drives. Resolve once at the top of the operation's funnel with `sync::identity::resolve_drive_identity(pool, account_id, label)` and thread the `DriveIdentity` down — two resolves in one operation can straddle a concurrent remove/re-add. Every engine config goes through `build_hcfs_config(server_url, bearer, &DriveIdentity)`.
- **Never re-derive or rewrite a member's folder seal.** A member's `enc_mnemonic.json` holds the OWNER's folder mnemonic, so `ensure_derived_mnemonic` and password rotation must skip member rows — re-deriving from the local master installs wrong key material and loses access to the data.
- A structurally-own site may build `DriveIdentity::own` directly, with a comment saying why the resolver is not needed.

Guard sites are counted by `tests/shared_drive_wiring.rs`, but a new call site it does not know about is not covered — resolve, do not derive.

## hcfs-client dependency

The sync engine delegates to `hcfs-client` (from the `hcfs` repo, pinned to a git rev in Cargo.toml). Drive API: `new()`, `init()`, `unlock()`, `sync_async(SyncMode)`, `stage()`, `set_config()`, `set_progress_handlers()`. All file encryption is handled by hcfs-client via BIP-39 mnemonic.

`Cargo.toml` pins `hcfs-client` / `hcfs-shared` to the same merged hcfs `main` rev. The weekly `hcfs-bump` workflow advances it; CI's wire-contract guards gate the result. **Run the live e2e lane on every pin bump** (see `testing.md`).

**`main.rs` must call `hcfs_client::cpu_pool::configure(CpuPolicy::Background)` before the Tauri builder.** hcfs hashes and encrypts on a rayon pool it owns, and that pool takes every core at default OS priority unless the host opts out — deliberately, since a library must not deprioritise its embedder's work uninvited, and the CLI/e2e/benches want `Full`. Without the call a large add pins every core and the window stops painting; nothing anywhere reports it, because the sync is otherwise correct. Ordering is half the contract: the policy is read when the pool is first built and the first build wins, so a call placed after any scan/hash/encrypt is indistinguishable at runtime from no call at all. `configure` returns the policy already in force rather than no-op'ing, and `main.rs` warns on that. Pinned by `tests/cpu_policy_pin.rs`, which checks the argument, the ordering against `Builder::default()`, and that hcfs still reports a late call.

## Multi-drive sync

Drives are keyed by label string. `trigger_sync` fans all drives out concurrently via `tokio::spawn`, each holding its own per-drive lock. `SyncActivityItem` includes a `label` field; all Tauri events include `"label"` in the JSON payload. DB constraint: `UNIQUE(owner, label)` in the sync_paths table.

**Label allocation is atomic** (`sync/paths.rs`): `set_sync_path_internal` takes a `LabelMode` (`Exact` upsert vs `Allocate { base }`) and, for the add-a-folder path, suffixes the unique label (`tags` → `tags-2`) INSIDE its own `BEGIN IMMEDIATE` transaction — not in the caller. This closes a TOCTOU where two concurrent same-basename adds computed the same label and the second's `ON CONFLICT DO UPDATE` silently overwrote the first drive's path (one drive survived, file sets merged on restart — a data-loss bug). `Allocate` plain-`INSERT`s so the `UNIQUE(owner, label)` constraint is the hard-error backstop; `Exact` keeps the upsert the set/update callers rely on.

**Deleting a remote folder is idempotent** (`sync/folders.rs::delete_remote_folder`): hcfs-server commits the folder-row delete before its long per-chunk storage cleanup, so on a large folder the client read can time out after the delete is durable. On an `unregister_folder` error the desktop re-lists remote folders (`remote_folder_absent`) and reports success when the folder is already gone, instead of a false "delete failed".

**"Is this drive configured locally" is a `sync_paths` question, never a `state.sync.drives` one.** The in-memory map holds only drives whose sync loop is registered: `pause_drive` drops the slot and `auto_init_sync` filters paused rows out of the init loop, so a paused drive — or one still mid-init on a slow login — is absent from it while its row, the user's standing intent, persists. `delete_remote_folder` asked the map and so skipped `remove_drive_for_account` for exactly those drives, stranding the row after the server wipe. Use `sync::paths::sync_path_exists`; `get_sync_folders_with_stats` carries the same lesson for its status column.

**An own drive whose server folder vanishes is RE-CREATED, not torn down.** hcfs-client runs `check_and_recover_remote_folder` at the top of every cycle; for an own drive missing from the listing it re-registers the folder and deletes the local `sync_state.json`. That baseline is what `SuspiciousEmptyRemote` is anchored on, so with it gone the next plan classifies the whole tree as new uploads. Net effect: **deleting a folder from the web console does not stick while a device still syncs it** — the folder reappears and the drive re-uploads, billed as new. The engine announces it via `SyncEvent::FolderRecovered` → `hcfs_folder_recovered`, which `useFilesNotification` turns into a "Folder Restored" notification (`SyncNotificationOutcome::FolderRestored`); before that listener existed the event had no consumer and the re-upload reached the user unexplained. Member drives are exempt — a vanished folder is revocation, and the destructive recovery is explicitly refused for them. Making console deletes stick needs a server-side delete tombstone: from the client, "the user deleted it" and "the server lost it" are the same absent row.

## Per-drive sync status

Owned by Rust as the single source of truth — there is NO global "sync engine status" enum, no global "user stopped" flag, no global "Syncing is currently stopped" banner. Every locally synced folder is one drive, and each drive has its own status computed from `sync_paths.is_paused`. Full design in `src-tauri/src/sync/drive_status.rs`.

- **`DriveStatus` enum** (`Active | Paused | Error { message }`) and **`DriveStatusEntry`** (`{ label, folder_name, status }`). Wire format is tagged (`{"kind": "active"}`, `{"kind": "error", "message": "..."}`). The `Error` variant is live — `initialize_sync_inner` constructs it on init failure so the FE can render a retry affordance without a second IPC round-trip; the FE must handle all three variants. `folder_name` is the basename of the sync path, shown in tray submenus and per-drive UI rows.
- **`get_all_drive_statuses` IPC** returns one entry per `sync_paths` row for the current account, skipping the internal `migration` pseudo-drive. Called by the frontend on mount to bootstrap the per-drive map.
- **Two events**: `hcfs_drive_status_changed` (`{label, status}`) on a single-drive Active ↔ Paused transition; `hcfs_drive_removed` (`{label}`) when `remove_drive` deletes a drive's row.
- **`pause_drive`** sets `is_paused=true`, removes the drive from the in-memory map, emits Paused. **`resume_drive`** clears `is_paused` and calls `initialize_sync_inner` (which emits Active on success). `initialize_sync_inner` ALSO clears `is_paused` itself after a successful init — the funnel invariant "successfully initialized ⇒ is_paused = 0" holds for every entry point (all three resume surfaces call `resume_drive`).
- **Epoch model** serializes pause/init races: `AppState.drive_lifecycle` (`sync::lifecycle_guard::DriveLifecycle`) holds per-label pause epochs + commit locks, and every *runtime* lifecycle write to `sync_paths.is_paused` happens under the label's commit lock — a single-writer protocol (startup one-shot migrations are exempt by construction: they run before any init can race). Producers: `pause_drive` and `remove_drive_for_account` bump the label's epoch under the lock before their in-memory removal + DB write; `stop_sync` bumps every registered label. Consumer: `initialize_sync_inner` snapshots the epoch at entry and commits via `apply_init_commit` — `Committed` clears the flag and emits Active; `Superseded` does a terminal in-memory teardown and returns `NotReadyKind::SupersededByPause` with no status emit (the FE falls back to the DB-derived Paused). Lock hierarchy: `commit_lock(label) → sync.drives → progress mutexes`. Pinned by `tests/drive_status.rs` and `tests/drive_lifecycle_race.rs`.
  - Known gaps: an init still in its pre-register window is not covered by `stop_sync`'s bump; identity-aware slot teardown, DB-sourced `stop_sync` bump labels, and epoch-gating `spawn_folder_registration` are tracked follow-ups.
- **`remove_drive`** deletes the `sync_paths` row, tears down in-memory state, and **wipes the on-disk sync baseline** (`sync_state.json` + `.bak` via `clear_persisted_sync_state`) so a future re-add of the same label cannot mistake a stale `synced` tree for "the server deleted these files" and propagate that to `local_deletes` — a data-loss bug fixed in commit `17b8e159`. User data files in the sync folder are left untouched. `pause_drive` deliberately preserves the baseline because pause is the reversible counterpart and depends on it to resume cheaply. Emits `hcfs_drive_removed`. There is no global "Stop Sync" button.
- **`stop_sync`** is internal cleanup only (logout, login, reset). It does NOT touch persisted state — `is_paused` rows survive logout/login because they represent user intent.
- **`auto_init_sync`** filters out paused paths and emits per-drive Paused for each before the init loop. For each successful init, `initialize_sync_inner` emits Active. There is no global aggregation; every status emit is per-drive.
- **Frontend mirror**: `driveStatusesAtom: Map<label, DriveEntry>` in `app/lib/global-atoms/unpinAtoms.ts`, populated by `useDriveStatuses` (mounted in `SyncEventLogger`). Derived `hasConfiguredDrivesAtom` answers "does the user have any drives configured" — used by upload buttons to gate the "set up sync first" toast. **Frontend code must never mutate `driveStatusesAtom` directly** — call the corresponding IPC (`pause_drive`, `resume_drive`, `remove_drive`) and let the event listener propagate the change.
- **Three pause/resume surfaces** share the same atom: the 3-dot menu in `MultiFolderSyncManager` (settings → Sync & Storage), the per-folder tab menu in `FilesContainer`, and the **Sync Folders** tray submenu in `useTraySync`. All call the same IPCs and read pause state from the same atom — no local mirrors.
- **Legacy migration**: existing users with the old global `user_preferences.sync_user_stopped = true` flag get every `sync_paths` row painted `is_paused = true` on first launch via `sync/user_stopped_migration.rs`. Idempotent, runs at every startup, safely deletable once enough releases have shipped.

### Per-drive exclusions

`sync/drive/selective.rs`. Exclusions exist so the USER can say "not that" — they are the backing store for selective sync (the folder browser records unticked subfolders as exclude patterns), stored as globs in `<sync-root>/.hippius/exclude` and re-read by `ExcludeRules::load` at the top of every sync cycle, so an edit applies on the next cycle with no restart.

**There are deliberately NO default exclude patterns.** A `DEFAULT_EXCLUDE_PATTERNS` seed was tried and reverted (commit `8bb84bdf`): everything a user puts in a drive must sync unless they say otherwise. Seeding `dist/`/`build/`/`target/` silently stopped backing up any folder a human happened to name that, which is the worst failure this product has — a skipped file looks backed up and is not. The wall of "File was modified during encryption" rows that motivated the seed is a PRESENTATION bug, fixed properly by the `ChangedWhileUploading` reclassification. If the credit cost of a huge regenerable tree is worth addressing later, do it as a visible prompt at drive-add time ("this folder contains node_modules, 42,000 files — exclude it?"), never as a silent rule.

Users edit patterns via `ExclusionsDialog` (settings → Sync & Storage 3-dot menu, and the same menu in `DriveOnboarding`), which is presentation only: `validate_pattern` in Rust owns every rule, including refusing a catch-all (`*`, `**`, `/` — anything made ENTIRELY of `*` and separators), which would otherwise silently stop the whole drive syncing with no error anywhere. The FE deliberately has NO mirror of those rules; it surfaces whatever Rust refuses.

**A folder row's totals are walked under the same rules that hide its contents.** `dir_stats_recursive` takes a `DirStatsExcludes { root, patterns }` — `root` is the DRIVE root even when a subfolder is walked, because the listing tags rows with drive-relative paths and the two must match. The memo is keyed on `(directory, ruleset)` with `(mtime, size, count)` as the value: the ruleset is a *map* key, not a validity field, because editing `.hippius/exclude` moves no directory's mtime (a two-part key serves pre-exclusion totals for the rest of the session — H-110: a row reading "3 files" above a view showing 1) AND because a map keyed on the path alone holds one ruleset's answer per directory, so the rule-less billing probe (`storage_overview::local_bytes_for_paths`) and the listing's patterned walk would overwrite each other on every refresh and neither would ever hit. A mismatched key is always a miss, never a wrong answer, so every invalidation path must drop **all** rulesets for the affected paths. The probe still passes `None` — it has no drive label to resolve patterns from — so a drive whose only un-uploaded bytes are excluded reads as indexer lag and pins the storage card on "Updating…". An excluded folder gets no walk at all (every consumer drops the row). Pinned by `the_walk_skips_what_the_patterns_exclude`, `a_directory_pattern_prunes_the_whole_subtree`, `changing_the_patterns_does_not_serve_the_previous_totals`, `a_child_walk_relativizes_against_the_drive_root_not_the_walked_folder`, `a_rule_less_walk_leaves_the_listings_entry_in_place`, `change_invalidation_drops_every_ruleset_for_the_affected_paths`, and `tests/exclude_glob_wiring.rs`.

**Glob matching is the engine's `ExcludeRules`, not exact path equality.** `sync/fileops/files/exclude_match.rs` wraps `hcfs_client::drive::ExcludeRules` and is the one matcher for Drive listing (`listing.rs`), recursive user-files (`user_files.rs`), and the recent-files activity feed (`recent.rs`). Every source the grouped listing merges must apply it — the on-disk walk, the server-only overlay, AND the `folder_entries_local` empty-folder cache. Nested excluded paths still contribute nothing, so `vendor/node_modules/a.js` cannot conjure a `vendor` folder. **Excluded files stay as rows** tagged `sync_status = "excluded"` (H-045: silent drop was the bug); **excluded folders stay off Drive**. `is_counted_for_label_stats` omits both from billed File No / storage. Recent Files omits matching rows at read time. `add_exclude_pattern` / `remove_exclude_pattern` emit `hcfs_activity_updated` and `trigger_sync` after a write. Do not resurrect `DEFAULT_EXCLUDE_PATTERNS`. Behaviour is pinned by `tests/list_sync_folder_nested.rs`; `tests/exclude_glob_wiring.rs` holds the source pins.

**The semantics are globset's, not gitignore's** — the module doc on `exclude_match.rs` carries the detail and the tests pin each one. The three that surprise people: every pattern is UNANCHORED (`docs/notes.txt` also matches `archive/docs/notes.txt`), `*` CROSSES `/` (so `build/*` covers the whole subtree), and matching is CASE-SENSITIVE even on macOS/Windows. Do not "fix" the case rule to match the filesystem: the engine would still upload `foo.bin` under a `*.BIN` rule, so a case-insensitive listing would hide a file that is being backed up — the listing must agree with the engine, not with the volume. `validate_pattern` compiles each pattern the way `ExcludeRules::parse` will (`globset`, same expansions) and refuses one that does not compile; upstream merely `warn!`s and drops it, which left the user with a rule listed as active that matched nothing.

KNOWN GAPS (not regressions, but they surface now that exclusions actually hide rows): `dir_stats_recursive` counts excluded children, so a folder row can read "12 files" and open showing 10, and its bytes land in the drive total; `synced_paths_and_excludes_for_label` and `recent.rs::collect_label_exclude_rules` both return NO patterns when the per-drive `try_lock` fails, so excluded rows briefly reappear while that drive is mid-sync; `compute_startup_pending_summary` ignores excludes by design and its "rare; a handful of files at most" rationale no longer holds.

## Logging in the sync hot path

**A per-item `info!` on a sync-engine callback is a support-bundle bug, not just noise.** The bundle `utils::logs` attaches to a ticket keeps a 5 MB TAIL per file (`MAX_BYTES_PER_FILE`), so anything logged per file competes directly with the diagnostics support needs — and wins, because there are always more files than errors. A drive holding a build tree (~80k files) produced ~340 lines/second from the scan callback alone, crowding a whole day's log down to ~65 seconds of coverage.

The scan callback (`sync::drive::lifecycle::callbacks::build_scan_callback`) is thinned by `LogThrottle` to at most one line per `SCAN_LOG_INTERVAL` (2s), deliberately NOT demoted to `debug!`: a slow scan is the phase users report as "stuck", so the line must survive in a default-level bundle. The throttle is NOT purely leading-edge — a 46-file scan finishes in 0.9ms, so sampling alone would log `1 files scanned` every cycle and never the total. Scan counts rise monotonically and restart at the next scan, so a DROP is the scan boundary (the only signal the callback gets — hcfs-client has no scan-complete callback), and `LogThrottle::decide` reports the previous high-water mark there. That check also resets the interval, so a cycle starting inside the previous cycle's window cannot fall silent. Wiring is pinned by `tests/scan_log_throttle_wiring.rs`, which COUNTS the logging sites in `build_scan_callback` — asserting only that the throttle is called would still pass with an unconditional `info!` reinstated beside it.

**Rule for new code:** a callback that fires per file/chunk/entry either throttles its log or logs nothing. Per-PAGE callbacks (e.g. `build_fetch_callback`, ~17 calls per cycle) are fine unthrottled.

## Progress events

**Pre-plan and per-chunk progress reaches the FE only via the throttled snapshot.** There is no `hcfs_scan_progress` / `hcfs_fetch_progress` / `hcfs_upload_progress` / `hcfs_download_progress` Tauri event — the first two existed with zero frontend listeners and were removed, the latter two never existed. The scan and fetch counters travel on `sync_progress_snapshot` as `preparingScannedFiles` / the `Fetching` preparing activity (`sync::preparing`), which rides the 250ms snapshot throttle and is what `SyncStatusDialog` and `traySyncSummary` read. `tauri_bridge.rs` handles all four `SyncEvent` variants in one no-op arm. **Do not add a per-item event**: `ScanProgress` alone fires ~80k times per cycle on a large drive, and the webview has no consumer for it.

**Per-file sync completion**: hcfs-client's `on_file_synced` callback fires per-file after the upload (or download + AEAD-verifying decrypt) succeeds. `build_file_synced_callback` calls `crate::sync::progress::mark_file_synced` to transition that single file's progress status to `Completed` immediately, instead of waiting for the entire cycle to finish in `complete_pending_files`. Without it a small decrypted file stays pinned at "Decrypting" while a large file downloads alongside it.

## Listing / SQLite performance

The synced-path cache is authoritative for Files listings — do not `load_sync_state` (full `sync_state.json` parse) on every IPC when the cache is warm. `dir_stats` fills the subtree on one `spawn_blocking` walk. **Every path that mutates the sync tree must call `invalidate_dir_stats_for_change(sync_root, changed)`** — `delete_files` and all three `add_*` commands do. The cache key is `(path, directory mtime)` and POSIX stamps only the directory whose own entries changed, so a create/remove one level down leaves every ancestor validating against its old mtime. It drops the subtree under `changed` (a removed directory, or a destination an add merged into) plus each ancestor by EXACT key up to the sync root — never by subtree, or one delete would discard every folder the user already browsed. Both arguments must be the listing form (DB sync path + relative); `list_sync_folder` never canonicalizes, so a `/private/var` key would miss every `/var` row. A completed cycle that downloaded or locally deleted files clears the whole memo (`invalidate_dir_stats_after_cycle` from `handle_sync_completed`) — a cycle touches arbitrary depths on any drive and `FileSyncedFn` cannot resolve its drive root synchronously. Drive teardown still uses `invalidate_dir_stats_under` on the whole root. The cache is process-wide, so its tests hold `dir_stats::CACHE_TEST_LOCK`. Files-page recursive search walks on `spawn_blocking`; do not reintroduce per-entry `tokio::fs`. `record_plan` and `folder_entries_local` writes are chunked/transactional. Snapshot overlay must not query SQLite for a stale emit `seq`. `folder_entries_local` is scoped by `account_key` and is cleared on `remove_drive`. Billing indexer caches (`drive_credits` / `drive_storage`) are per-account single-flight (`billing/account_cache.rs`) — never hold one global mutex across the fetch. Preview-cache eviction (`remote.rs`) drops files older than 7 days only when the directory exceeds 1 GiB, never `.part` temps or the file just written.

## Asset protocol scope

The static scope in `tauri.conf.json` is `$HOME/.hippius/preview-cache/**` — ONLY the decrypted-preview cache written by `cache_remote_file`, deliberately NOT all of `~/.hippius`: the wider scope let the renderer fetch `master_enc_mnemonic.json` and `hippius.db` via `http://asset.localhost`. User-chosen sync folders live at arbitrary paths, so the scope is expanded at runtime via `app.asset_protocol_scope().allow_directory(path, true)`. This happens in three places: `set_sync_path`, `initialize_sync_inner` (on every sync start/restart), and the frontend `tryAutoInitSync` (belt-and-suspenders at login). The `allow_asset_scope` IPC is also exposed. Helper `allow_asset_directory()` lives in `sync/files/asset_scope.rs`.

## Rename

**Rename detection**: The file watcher captures OS rename events (From/To pairs from the `notify` crate) and stores them as `RenameHint` structs in `SyncRunner.rename_hints`. Before each sync cycle the hints are drained, converted to relative paths, and expanded into per-file hints. The pairing/expansion logic lives in `hcfs-client`. When hcfs-client gains rename support (thenervelab/hcfs#52), the hints will be passed through to avoid redundant delete+re-upload cycles.

**File/folder rename** is one Rust IPC — `rename_entry` (`sync/files/rename.rs`), mirroring `delete_files`: resolve label→sync path via `resolve_rename_root` (an explicitly-named label MUST exist — no silent default-drive fallback, which could rename a same-named entry in the wrong drive; only label-less entries use the default drive), `derive_relative_name`, validate the new basename (`validate_new_name`: non-empty, ≤255 bytes, no separators/`.`/`..`/NUL, plus Windows safety — no `:`, no trailing dot, DOS reserved device names like `con.txt` rejected; the FE validator in `renameValidation.ts` mirrors these for instant feedback), then `tokio::fs::rename` + `trigger_sync`.

Server propagation is a **true rename, not delete+re-upload**: the hcfs-client file watcher captures the programmatic `fs::rename` exactly like a Finder rename (Tier 1 hint → `SyncPlan` rename extraction → server batch-rename endpoint), and the content-hash Tier 2 fallback covers a missed hint. The command deliberately does NOT call `SyncRunner::push_rename_hint` — the watcher already produces the hint, and a duplicate would put two renames with the same target hash into one batch, which hcfs-server's `validate_rename_batch` rejects WHOLESALE (forcing every rename that cycle into the delete+re-upload fallback).

Two guards in `rename_entry_inner`: (1) destination pre-check with canonical-path same-entry comparison, because Unix `rename(2)` silently replaces an existing destination while case-only renames ("a.txt"→"A.txt") legitimately "exist" on macOS's case-insensitive APFS; (2) folder renames are refused while the drive's **last-synced** rel-path set (`synced_paths_for_label`) contains children missing on disk — a conservative "folder is mid-sync" check. The guard queries the same `guard_label` whose root resolved the rename path, so the default-drive fallback can never probe one drive's rel-paths against another drive's filesystem. KNOWN GAP: children uploaded from another device and never downloaded here are absent from that set, so a folder rename can still leave the next sync re-creating the old folder name for them (the same thing happens for a Finder rename today); closing it needs an engine-side accessor over hcfs-client's `state.remote`.

FE: `renameModalFileAtom` (`app/lib/global-atoms/renameAtoms.ts`) + one `RenameDialog` mounted in `app/(pages)/layout.tsx`; `useRenameFile` wraps the IPC and mirrors `useDeleteFile`'s refetch set. All surfaces share the `canRenameFile` gate (`app/lib/utils/renameGating.ts`): enabled only for `isAssigned`, locally-present, settled rows — cloud-only rows from other devices show the item disabled with a tooltip. Wired into `createTableItems`, the card view menu, and `FileContextMenu`.

## Keep-awake during active sync

While any sync session still has non-terminal files, the Rust backend holds an OS "prevent idle **system** sleep" assertion so macOS/Windows can't sleep mid-transfer — exactly what Finder does during a copy. Display sleep is deliberately never blocked. No frontend surface, no toggle.

Mechanism: the `keepawake` crate (pinned `=0.6.0`; macOS `IOPMAssertionCreateWithName(kIOPMAssertionTypePreventUserIdleSystemSleep)`, Windows `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` — no `ES_DISPLAY_REQUIRED`), a **macOS/Windows-only** target dependency; Linux no-ops for v1 because keepawake's Linux backend drags the zbus D-Bus stack for a nice-to-have. `src-tauri/src/power.rs` owns the feature: the pure resolver `should_hold_keep_awake(&SyncSnapshot)` (hold iff `is_active && completed_files + failed_files < total_files`; empty heartbeat cycles and the stalled-completion shape both release), the `SleepBlocker`/`SleepGuard` trait seam (RAII guard; the native blocker parks the keepawake handle on a **dedicated thread** because Windows' `ES_CONTINUOUS` state is bound to the creating thread — create and Drop must happen on the same thread), and the edge-triggered `SyncKeepAwake::apply` at `AppState.keep_awake` (idempotent per edge; an acquire failure is logged, not latched, so the next frame retries).

Wiring is in `sync/projection/tauri_bridge.rs`: `handle_progress_snapshot` re-evaluates on EVERY frame (the safety net — a missed terminal event is corrected by the next idle frame), plus explicit `reevaluate_keep_awake` on `SyncStopped`/`SyncReset`/real `SyncError` for teardown orderings with no trailing snapshot. Process exit releases inherently. Pinned by the resolver + fake-blocker unit tests in `power.rs` and `tests/keep_awake_wiring.rs`.

## Reclaiming abandoned upload chunks

Every upload stages a FULL encrypted copy of the file at `~/.hippius/drives/<account>/<folder>/temp/upload_<file_id>/` before a byte leaves the machine. hcfs-client deletes that directory on a successful finalize (`cleanup_upload_chunk_dir`) and on `InsufficientBalance`, but on **every other exit** — network error, 5xx, a finalize that timed out, or a cancel from pause/stop/logout/the 180s stall watchdog — it keeps the chunks DELIBERATELY as a re-encryption cache. That retention has no ceiling and, in practice, no reaper; it can fill a disk.

Three structural holes in the engine's own pruning, each worth knowing before touching this:

1. The **orphan prune** keys on the `file_id` being absent from local+remote+synced — a file still on disk awaiting upload is by definition in `local`, and one whose finalize timed out but landed server-side is in `remote`+`synced`, so both are structurally immune.
2. The **age prune** keys on `manifest.encrypted_at`, which is RE-STAMPED on every re-encryption, so a file that fails and re-encrypts each cycle refreshes its own clock forever.
3. Both run only INSIDE a sync cycle, so a paused drive, a stopped sync, or a closed app reclaims nothing.

The failure is self-reinforcing: once free space runs low, `check_disk_space` fails every encryption with `SyncError::Encryption` — a keep-the-chunks variant — so the cache can only grow.

The desktop-side reclaim is `sync/shared/chunk_reclaim.rs` (re-exported at `crate::sync::chunk_reclaim`), deliberately independent of the pinned hcfs-client so existing users get their space back with no dep bump. The pure, unit-tested `plan_reclaim` applies three rules:

- **Incomplete** — no readable manifest. An unparseable one reads as `None` ON PURPOSE, because hcfs-client's own `UploadChunkManifest::load` would reject it too and the two must not disagree about what is live.
- **Expired** — older than `RESUMABLE_MAX_AGE_SECS` (**24h**, matching hcfs-server's `UPLOAD_SESSION_TTL_HOURS`). Deleting is NOT free: the directory is an ENCRYPTION cache, not a session cache — `validate_cache` checks only the plaintext salted hash and the chunk sizes, so even a stale directory still lets `upload_file_standalone` skip re-encryption against a brand-new session. What expiry forfeits is exactly that one re-encryption. Past the TTL the re-upload was already unavoidable, and a directory that has not completed in 24h is overwhelmingly abandoned.
- **OverBudget** — survivors are evicted oldest-first only while the cache exceeds `CHUNK_CACHE_BUDGET_BYTES`, aggregated across ALL drives. Expired bytes are NOT counted against the budget, or a single stale directory would evict live ones for nothing.

**The once-per-process latch is load-bearing, not an optimization**: the budget rule can delete a still-resumable directory, which is safe only because the pass runs before any drive has started uploading. It is awaited through `AppState.chunk_reclaim` (a `tokio::sync::OnceCell`) at the top of `initialize_sync_inner` — the single init funnel — so the first init runs it with nothing in flight and every later init reads the cached summary and touches no files. Running it per-init would let it evict the chunks an active upload is streaming.

**There are TWO triggers on that one cell, and both are needed**: `setup()` in `main.rs` is the LAUNCH trigger, because `auto_init_sync` filters out paused drives and so the init funnel alone would reclaim nothing for a user who reacted to a full disk by pausing every drive; the `initialize_sync_inner` call is the ORDERING guarantee. Whichever fires first runs the pass; the other awaits its result. The launch spawn MUST sit after `app_handle.manage(app_state)` — `state::<AppState>()` panics if a Tokio worker wins the race with setup (H-005). `try_state` is not a substitute: a `None` skip reopens the paused-drive hole. Pinned by `tests/chunk_reclaim_wiring.rs` (`launch_reclaim_runs_after_appstate_is_managed`).

`remove_drive` additionally wipes the whole `temp/` beside `clear_persisted_sync_state`: the drive is gone, so its staged chunks are unreachable by every other path, and a user removing a drive to free disk must actually free it. That wipe goes through `spawn_blocking` — the tree can hold tens of GB across thousands of files, and unlinking that many inline would stall a Tokio worker and the IPC response for seconds (the two-`unlink` `clear_persisted_sync_state` beside it is not a precedent).

The scan enumerates temp dirs from the FILESYSTEM, not from `sync_paths` — drives removed before this shipped left staging directories with no row pointing at them, and those are exactly the bytes nothing else can reach. It covers BOTH `~/.hippius/drives/<account>/<folder>/temp` and the legacy `~/.hippius/drives/<account>/temp`: `run_migration`'s Legacy-B branch COPIES the account-level tree into the per-folder config dir and never deletes the source. Non-`upload_` entries (download-resume state, decrypt temps) belong to hcfs-client's other pruners and are left strictly alone. Pinned by the unit tests + `tests/chunk_reclaim_wiring.rs`, which asserts the call EXISTS, goes through `get_or_init`, precedes drive registration, and that the launch spawn sits after `app_handle.manage(app_state)` (a spawn above `manage` panics `state() called before manage()`).

KNOWN GAP (tracked hcfs follow-up): the budget is enforced at startup only, so growth WITHIN one long run is still unbounded — closing that needs the engine-side changes (48h→24h, a non-resetting age clock, and cleanup on the cancel path), since only hcfs-client knows which directories are live mid-cycle.

## Failure and cancel notification policy

**Cancels never notify.** User-initiated cancels (`pause_drive`, `remove_drive`, logout's `stop_sync`, `teardown_previous_drive`) and the internal stall-watchdog self-cancel all surface as `hcfs_client::sync::SyncError::Cancelled`, which stringifies to `crate::sync::events::CANCELLED_MARKER` ("Operation cancelled by user"). `TauriSyncBridge::on_event` drops any `SyncError` whose message equals that marker — cancels never reach the `hcfs_sync_error` channel, so they never create persisted "Sync Failed" rows and never clear `pendingConflictsAtom`. Stall-watchdog cancels are silenced through the same path because hcfs-client auto-retries them and `FILES_FAILED_REPEATEDLY` surfaces anything that persistently fails. `sync::events::tests::cancelled_marker_matches_upstream` pins the marker to `SyncError::Cancelled.to_string()` so an hcfs rev bump fails fast if the upstream wording drifts.

Notification rows are outcome-tagged: `create_sync_notification` takes a `SyncNotificationOutcome { Success, Error }` driving the title ("Sync Complete" vs "Sync Failed") and the `notification_subtype` prefix (`FileSyncComplete-` vs `FileSyncError-`).

**Flaky-endpoint gating**: a non-cancel `SyncError` is emitted by hcfs-client on *every* failed retry cycle, so turning each into a notification spams the bell. The bridge emits the raw `hcfs_sync_error` event unchanged (its live consumers — `ConflictEventListener` dropping pending conflicts — must see every real error) but routes the *persisted notification* through a separate, gated `hcfs_sync_failed_notify` event. `handle_sync_error` takes a `FailureNotify { Gated, Always }` policy: the auto-retry loop passes `Gated`, the user-initiated reviewed-conflict path passes `Always`. Under `Gated`, the gated event fires only when `crate::sync::error_notify::ErrorNotifyState::record_failure` returns true: a **per-label** consecutive-failed-cycle counter (`HashMap<label, u32>` on `AppState.error_notify`) that fires once when a drive's own count first reaches `ERROR_NOTIFY_THRESHOLD = 3` and suppresses every later cycle until recovery.

**Counting per-label on the desktop is deliberate**: the `consecutive_failures` on the `SyncError` payload is a runner-*global* `AtomicI64` that any healthy drive's success resets every cycle (`trigger_sync` fans out all drives concurrently), so gating on it would never let a single down drive in a multi-drive account reach the threshold. The count is reset by `clear` on the recovery edge (`handle_sync_completed`) and `SyncStopped`, and globally by `clear_all` on `SyncReset`, deliberately **not** on `SyncStarted` (which fires before every failing cycle). `useFilesNotification.ts` listens to `hcfs_sync_failed_notify`, not `hcfs_sync_error`.

KNOWN GAP (under-notification, never spam): hcfs-client's `NoChanges` outcome resets its global counter but emits no `SyncCompleted`, so a drive that recovers while idle never reaches `clear`; its count stays at/above threshold and a later outage is suppressed until a cycle that actually transfers files emits `SyncCompleted`. Closing it needs a per-label "cycle ok" signal from hcfs-client on `NoChanges`, or clearing on the global `HealthChanged → Connected` transition.

## Reviewed conflict sync (conflicts banner → "Sync Now")

Mid-cycle conflicts raise `hcfs_conflicts_pending` (per-label `pendingConflictsAtom` → `ConflictsBanner` → `StagedChangesDialog`).

The `sync_with_conflict_resolutions` IPC (`sync/drive/control.rs`) **`try_lock`s the drive manager — never a blocking lock**: the auto-sync loop holds that same per-drive lock for an entire cycle (`run_sync_cycle` in hcfs-client), which on a large drive runs for tens of minutes, and a blocking `lock().await` silently queues the user's "Sync Now" click behind the in-flight cycle with the button spinner as the only feedback. Contention returns `NotReady(SyncInProgress)` with no UI/watcher side effects — `is_syncing`, the `SYNC_STARTED` emit and watcher suppression are applied only after acquisition — and **re-arms review mode** (best-effort `set_drive_review`; refused during the post-review cooldown) so the auto-sync loop pauses at the next cycle boundary and the user's retry wins the lock deterministically instead of racing the loop's 5s tick. Ordering, lock discipline, and re-arm are pinned in `tests/hippius_conflict_resolution.rs`.

FE: `useStagedChanges.syncWithResolutions` returns `{ok: true} | {ok: false, message, syncInProgress}`. `ConflictsBanner.handleSync` **closes the dialog immediately on submit** and hands progress to the sidebar sync widget, then drops the banner **only on success**; on failure it keeps the banner and toasts. `sync_with_conflict_resolutions` runs the ENTIRE cycle inline, so keeping the dialog open for the call meant minutes of a modal spinner with Cancel/X/Escape disabled.

Note the `skip` resolution verb **defers** a conflict (the engine re-detects it next cycle and the banner returns) — the dialog labels it "Skip for now" and warns explicitly when *every* conflict is set to skip, since that satisfies the "resolve all N conflicts" gate while resolving none.

## Download Folder as zip

Nested "Download Folder" (and a folder row's Download action) saves a **store-only `.zip`**, not a copied directory tree. Rust owns the pack: `export_folder_zip` (`sync/fileops/files/export_zip.rs`) takes `{ sync_path, relative_folder, output_zip_path }`.

Gates match `export_file` — `sync_path` must be a `sync_paths` row for the active account (`require_registered_sync_path`, shared so the two IPCs cannot drift) and `relative_folder` must stay inside that root (`ensure_within` plus a Normal-components-only check that rejects `..` before canonicalize). The walk uses the skip set from the deleted share-time `zip_dir.rs`: Unix symlinks (not followed — a link out of tree is data exfil), non-UTF-8 names, backslash names, hidden entries. Windows junctions report as directories, so before pushing a dir the walk canonicalizes + `ensure_within(src_dir, child)` (fail closed on an out-of-tree target) and skips already-visited canonical paths (junction cycles). Empty directories are recorded as zip directory entries.

Each entry's DOS mtime is the source file's local mtime (not the zip crate default 1980-01-01); years outside 1980–2107 clamp. Compression is `zip::CompressionMethod::Stored` with `large_file(true)` so a single entry past 4 GiB uses per-file ZIP64. Bytes land on a unique sibling `.part` and are renamed onto dest only after `finish`; a pack error deletes the temp and never a pre-existing dest. An output whose canonical path sits under the packed folder is refused (`hcfs_client::drive::files::ensure_not_nested`). The walk + zip write run on `spawn_blocking`.

FE splits the OS save dialog (`pickFolderZipSavePath`) from the pack IPC (`exportFolderZipToPath`) so `DriveContainer`'s spinner starts only after a path is chosen; `downloadFolder` composes both for the files-table Download action. Do not overload `export_file`'s file-copy path for this.

## Nested folder listings

Nested folder browsing in the FE uses `list_sync_folder_grouped` (`sync/files/listing.rs`), which returns `{ folders, files, pending_backfill }` grouped by the first path component under the requested `subfolder`. The plaintext `relative_path` comes from hcfs-client's in-memory `path_index` — the server only stores an encrypted path + hash, never plaintext, so the desktop never "decrypts a server path"; it overlays the local rel-path cache onto the on-disk tree.

This overlay is what makes a not-yet-downloaded subtree visible: the directory doesn't exist on disk but the cache still knows the rel-paths, and the grouped listing surfaces them with `sync_status="pending"`. Pre-backfill drives (`sync_paths.relative_paths_backfilled_at IS NULL`) flip `pending_backfill=true` so the FE can render an "Indexing folders…" banner; the flag is owned by the one-shot backfill at `sync::relative_path_backfill::run_backfill_for_drive`, spawned from `initialize_sync_inner` — the single funnel every init path goes through. `tests/hippius_relative_path_backfill.rs` asserts `initialize_sync_inner`'s body references `spawn_backfill` so a refactor can't drop the trigger.

## First-class empty folders

Empty directories synced from the desktop appear in the web Console via a first-class server `folder_entries` entity (hcfs side). The desktop mirrors that entity set with a `folder_entries_local(owner, label, relative_path)` SQLite cache (`utils/schema.rs`) and a per-drive `sync_paths.folder_entries_backfilled_at` flag. Two write paths keep the server's folder entities and the on-disk directory tree in step, delegating to hcfs-client's `register_folder_entries` / `unregister_folder_entries` (local→server) and `list_folder_entries` (server→local).

- **One-shot backfill** (`sync/migrate/folder_entries_backfill.rs::run_folder_entries_backfill_for_drive`, spawned via `spawn_folder_entries_backfill` from `initialize_sync_inner`): for drives created before `folder_entries` existed, walks the sync root on `spawn_blocking`, registers every directory, mirrors them into `folder_entries_local`, and sets the flag. Gated to run once per drive (`is_folder_entries_backfilled`) and **never deletes** — a partial failure just retries next launch. `tests/hippius_folder_entries_backfill.rs` pins the spawn wiring.
- **Per-cycle folder-entity sync** (`sync/migrate/folder_entries_materialize.rs::run_folder_entity_sync_for_drive`, spawned via `spawn_folder_entity_sync` from `handle_sync_completed`): ONE sequential per-cycle task — reconcile (local→server) THEN materialize (server→local) — over a SINGLE shared disk walk, gated by ONE per-label `PerLabelThrottle` on `AppState.folder_entity_sync`. It is NOT two separate reconcile/materialize spawns or throttles. Both halves are no-ops until the backfill flag is set.

  The spawn takes a **`FolderEntitySyncTrigger`**: `PerCycle` applies the `MIN_FOLDER_ENTITY_SYNC_INTERVAL = 30s` interval — best-effort, since a skipped cycle is picked up by the next eligible one — while **`Forced`** (from `delete_files`, when the batch removed a DIRECTORY) skips the interval. `Forced` exists because a folder delete can produce no file work at all: hcfs-client ends that cycle `NoChanges` and emits no `SyncCompleted`, so the routine trigger may never fire and the folder would stay registered server-side AND keep reappearing in `list_sync_folder_grouped` through the cache overlay.

  `PerLabelThrottle` therefore carries a second, non-optional gate: an **in-flight set** handing out an RAII `RunPermit` (released on drop, including on panic). Bypassing the interval without it would let a forced run overlap a routine one, and an overlapping run's materialize can hold a server list fetched *before* the other's unregister landed — re-creating on disk the very folder being deleted. A `Forced` request refused by the in-flight guard is **queued, not dropped** (a `pending_forced` set): the running task serves it via `RunPermit::take_pending_or_release`, which checks the flag and releases the slot under the SAME `in_flight` lock `try_acquire` sets it under. A refused `PerCycle` request is simply skipped — the asymmetry is the point, since only the routine trigger has a guaranteed next occurrence. `clear`/`clear_all` reset the interval stamps and drop queued requests, but never the in-flight set: a teardown does not stop a running task, so force-freeing its slot would reopen exactly that overlap.

  A run that applied a delta emits **`hcfs_folder_entities_changed`** (`events::FOLDER_ENTITIES_CHANGED`, payload `LabelPayload`; condition owned by the pure `folder_entities_changed`), which `useSyncEvents` folds into the usual `sync_files_completed_changed` dispatch. This is the completion signal the FE otherwise lacks: `folder_entries_local` is only evicted AFTER the server unregister round-trip, so the frontend's own post-delete refresh — a local IPC that always wins that race — still reads the row and re-surfaces the deleted folder as `pending`. Steady-state `NoChanges` and deferred/transient outcomes deliberately do NOT emit, or every idle cycle would refetch every listing.

- **Reconcile half** (`folder_entries_reconcile.rs::reconcile_with_on_disk`): re-derives the on-disk-vs-cache directory delta (`compute_dir_delta`), registers newly-created dirs / unregisters removed ones, and is the **ONLY** writer of `folder_entries_local` (materialize never touches the cache). Stays **OUT** of the file reconcile loop — folder entities are a separate domain that touches no file rows (the entry-level unregister endpoint deletes zero files; a non-zero `files_deleted` is logged as a warning).
- **Materialize half** (`folder_entries_materialize.rs::materialize_with_on_disk`, via `list_folder_entries`): pulls the post-reconcile server set DOWN to disk — `create_dir_all`s directories the server has but disk lacks, and removes orphaned local directories the server has dropped, but ONLY when the dir is still EMPTY (`std::fs::remove_dir`, **never** `remove_dir_all`) AND present in the local cache (so a user's brand-new local folder — on disk, not yet cached — is never deleted). The emptiness guard `should_remove_orphan_dir` plus the non-empty-failing `remove_dir` close the TOCTOU window if a file lands mid-delete; `safe_join_under_root` rejects any server path that isn't a clean `Normal`-component relative path. Materialize imports no `SyncPlan`/file-tree types and never uploads or deletes a file.
- **Why one sequential task, not two concurrent spawns** (the resurrection race): a folder the user just deleted locally (`disk=no, cache=yes, server=yes`) is one the reconcile wants to UNREGISTER while a concurrent materialize, holding a stale pre-reconcile server snapshot, wants to CREATE — silently undoing the deletion. Running reconcile to completion FIRST means materialize's `list_folder_entries` fetch sees the post-unregister set, so `to_create = server \ disk` no longer contains it. Pinned by the hermetic plan/apply/guard unit tests + proptests in `folder_entries_materialize.rs` (incl. the `plan_over_stale_server_set_would_recreate_locally_deleted_dir` hazard doc) and the live-lane two-instance e2e in `tests/folder_entries_real_backend.rs`.

- **Grouped-listing overlay** (`sync/fileops/files/listing.rs`): `list_sync_folder_grouped` overlays the direct-child folders implied by `folder_entries_local` (`cache_only_folder_candidates`) onto the on-disk + file-derived listing, deduped via the `seen_names` set. The cache read is `owner`-scoped (`account_key`) so another account's rows can't leak in.
